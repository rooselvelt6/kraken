# Plan 2030 — Kraken

Objetivo: que Kraken compile, arranque y cumpla lo que promete, con **cero
impacto sobre el sistema principal** (openSUSE Tumbleweed). Toda compilación,
prueba y ejecución ocurre dentro de un entorno aislado desechable.

Motivo: la última ejecución sobre Fedora dañó el sistema operativo del host.
El host queda fuera del ciclo: solo aporta CPU, RAM, disco y el código fuente.

Decisiones ya tomadas:

- Alcance: plan completo (correcciones + módulos cableados).
- Permisos por defecto: `workspace-write` (nada se auto-aprueba).
- Se permite descargar crates (dentro del entorno aislado).
- Se compila el workspace completo.

## 0. Aislamiento (Fase previa, obligatoria)

### 0.1 Entorno por defecto: contenedor Docker

Es la vía rápida y la recomendada para compilar y testear. El host solo ve
carpetas montadas; nada de lo que pase dentro modifica el SO.

Base de trabajo: `rust:1.98-slim`, ya presente en el sistema (1.25 GB, sin
descarga adicional). Para replicar el entorno donde falló Fedora, usar
alternativamente una imagen Fedora de forma puntual.

```bash
# Crear red y volumen de caché (fuera del repo, datos descartables)
docker volume create kraken-cargo

# Crear el contenedor de trabajo, SIN privilegios
docker run -d --name kraken-build \
  --user "$(id -u):$(id -g)" \
  --cap-drop=ALL \
  --security-opt no-new-privileges:true \
  --pids-limit=4096 \
  --memory=8g --cpus=8 \
  --tmpfs /tmp:rw,size=2g \
  -v "$PWD":/workspace:rw \
  -v kraken-cargo:/cargo:Z \
  -w /workspace \
  -e CARGO_HOME=/cargo \
  -e RUSTUP_HOME=/cargo/rustup \
  -e PATH=/usr/local/cargo/bin:/usr/local/rustup/bin:$PATH \
  rust:1.98-slim sleep infinity
```

### 0.2 Reglas obligatorias del contenedor (el host no se toca)

Prohibido dentro del `docker run`:

- `--privileged`.
- Montar `/var/run/docker.sock` (equivale a root en el host).
- `-v /:/host` o cualquier montaje de `/etc`, `/boot`, `/usr`, `/var`, `/home`.
- Montar `~/.ssh`, `~/.aws`, `~/.config`, `~/.gnupg`.
- `--network=host`, `--pid=host`, `--ipc=host`.
- `--device` o `/dev` salvo `/dev/kvm` cuando corresponda.

En el host, prohibido: `sudo`, `zypper`, `rpm`, `modprobe`, `sysctl`,
`systemctl enable`, `iptables`, escritura en `/usr/local` o `/etc`, y ejecutar
cualquier binario de Kraken fuera del contenedor.

Nota: pertenecer al grupo `docker` equivale a root en el host. Por eso el
contenedor se crea siempre con las restricciones anteriores y nunca con
privilegios ni socket montado.

### 0.3 Entorno reforzado: VM con KVM, para lo que toca el kernel

Los módulos `wireless`, `c2`, `postexploit` y `mobile` necesitan paquetes
externos y, en wireless, interacción con interfaces. Eso **no** se prueba en
el contenedor: se prueba en una VM desechable con snapshot.

```bash
qemu-img create -f qcow2 /home/tdy/Imágenes/kraken-vm.qcow2 40G
qemu-system-x86_64 -enable-kvm -m 8192 -smp 8 \
  -drive file=/home/tdy/Imágenes/kraken-vm.qcow2,if=virtio \
  -snapshot \
  -netdev user,id=n0 -device virtio-net-pci,netdev=n0 \
  -cdrom /ruta/fedora.iso
```

- `-snapshot` garantiza que al apagar la VM se descartan todos los cambios.
- Red modo `user` (NAT), nunca `tap` ni `bridge`: la VM no se expone a la red
  local.
- El repositorio entra como un disco o directorio compartido de solo esos
  datos, nunca el HOME del host.
- Antes de cada prueba de riesgo: `savevm snapshot-base`; para volver:
  `loadvm snapshot-base`.

### 0.4 Qué se ejecuta dónde

| Actividad | Entorno |
|---|---|
| `cargo build`, `test`, `clippy`, `fmt` | contenedor Docker |
| Análisis estático, lectura de código, planes | host (solo lectura) |
| `/bughunter`, `/hunt`, escáneres de red | contenedor Docker |
| `wireless`, `c2`, `postexploit`, módulos root | VM KVM con snapshot |
| `kraken.service`, arranque como root | ninguno: no se instala |

12. **Fase 10 — Blindaje adicional (Recomendación experta)** 🔒 OPCIONAL

    Endurecimiento defensivo para entornos de alta amenaza:

    - **Audit trail inmutable**: `kraken-audit` crate con append-only log firmado (ed25519) de cada decision de permiso, tool call y sandbox event. Integración con `kraken-events` existente.
    - **Remote attestation**: TPM 2.0 quote del contenedor al arranque → verifica que el binario y config no fueron alterados. `kraken-infra` + `tpm2-tss`.
    - **Policy as code + GitOps**: `PermissionPolicy` serializable a TOML/JSON, versionado en repo, revisable en PR. `kraken-policy` exporta/importa.
    - **Supply chain verification**: `cargo-vet` / `cargo-crev` integrado en CI; `cargo deny` para licencias, bans, advisories. `cargo audit` en cada PR.
    - **Runtime integrity**: `kraken-infra::integrity` — hash SHA-256 de binarios críticos al inicio; re-verificación periódica via timer.
    - **Network egress control**: `kraken-infra::network` — allowlist dominios/IPs por tool (ej. `WebFetch` solo a allowlist). Seccomp + cgroups v2 `net_cls` + `iptables`/`nftables` en host.
    - **Secret scanning en runtime**: `kraken-infra::secrets` — detecta claves/API keys en memoria/archivos antes de que salgan del sandbox.
    - **Reproducible builds**: `CARGO_BUILD_RUSTC_VERSION=1.98.1`, `SOURCE_DATE_EPOCH`, `cargo build --locked --profile release-lto`. Verificación `diffoscope` en CI.
    - **Chaos testing**: `kraken-chaos` crate — inyección de fallos (OOM, net partition, CPU throttle, fs full) en tests de integración.
    - **Formal verification (opcional)**: `kraken-policy` crítico verificado con `kani` / `prusti` / `creusot` para propiedades de seguridad (ej. `permits()` nunca escala `Prompt`/`Allow`).

    *Esta fase no bloquea release; es para despliegues en infraestructura crítica, defensa, fintech, salud.*

Detenerse y reportar tras cada fase antes de pasar a la siguiente.
